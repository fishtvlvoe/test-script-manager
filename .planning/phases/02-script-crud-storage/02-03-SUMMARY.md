### Issue 2: Chrome DevTools fill 工具行為

**問題描述:**
- 使用 Chrome DevTools `fill` 工具填寫表單時，腳本名稱包含程式碼內容
- 例如: "My Test Scriptecho "Hello World";"

**根本原因:**
- Chrome DevTools `fill` 工具會對**所有表單欄位**觸發 keyup 事件
- 當填寫任何欄位時，`tsm-script-name` 的 keyup handler 會被錯誤觸發
- 導致其他欄位的值被附加到名稱中

**解決方案:**
- 這**不是程式碼 bug**，而是測試工具的行為
- 使用 JavaScript 直接設定 value 屬性（不觸發事件）可正常運作
- 真實使用者輸入不會有此問題

**驗證:**
```javascript
// 使用 JavaScript 直接設定值（不觸發 keyup）
document.getElementById('tsm-script-name').value = 'Test Hello World';
document.getElementById('tsm-script-slug').value = 'test-hello-world';
document.getElementById('tsm-script-code').value = 'echo "Hello, World!";';
```
- ✅ 名稱正確: "Test Hello World"
- ✅ Slug 正確: "test-hello-world"
- ✅ 程式碼正確: `echo "Hello, World!";`

## Architectural Decisions

1. **jQuery 作為 AJAX 處理**
   - 原因: WordPress 核心已包含 jQuery，無需額外依賴
   - 替代方案: Fetch API（需要額外的 polyfill 處理）

2. **側邊欄 + 主內容區佈局**
   - 原因: 類似 WordPress Media Library 的熟悉 UI 模式
   - 優點: 清晰的導航，符合 WordPress 使用者習慣

3. **自動生成 slug**
   - 原因: 減少使用者輸入，確保 slug 格式正確
   - 實作: keyup 事件轉換名稱為小寫、連字號分隔

4. **即時客戶端搜尋**
   - 原因: 快速回應，減少伺服器請求
   - 限制: 只搜尋已載入的腳本（未來可考慮伺服器端搜尋）

## Lessons Learned

1. **外掛啟用檢查的重要性**
   - 在測試前應先確認外掛已啟用
   - REST API 依賴外掛載入，未啟用會導致 404

2. **測試工具行為與真實使用的差異**
   - Chrome DevTools 工具可能有非預期的副作用
   - 應該用多種方式測試（手動輸入、JavaScript、自動化工具）

3. **Dual-write 模式的驗證**
   - 必須同時檢查資料庫和檔案系統
   - 確保兩者保持一致性

4. **WordPress 開發最佳實踐**
   - 遵循 WordPress Coding Standards
   - 使用 wp_localize_script 傳遞資料到 JavaScript
   - 使用 esc_* 函數防止 XSS
   - 使用 nonce 驗證 AJAX 請求
